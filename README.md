# Multi-Agent Playbook · 多 Agent 软件工程协作手册

> 一套「人类所有者 + 多个 AI Agent」长期协作做软件与知识工程的实操方法论。
> 一套在真实项目中反复打磨、长出来的 3.0 多 Agent 协作架构——本手册讲清它的结构、制度与教训。

## 这是什么

过去两年，个人与团队都在摸索同一件事：**怎样让 AI 参与的工程不失控**。
本手册整理的是一套经真实项目反复打磨、并已通用化的协作制度，回答三个问题：

1. **架构**：谁是决策者？协调、执行、复核怎么分工才不打架？（[01](01-架构总览.md)、[02](02-设计与执行分工.md)）
2. **资产**：怎么把「AI 会用的方法」沉淀成可治理的 skill 库，并让任务自动路由到合适的 skill？（[03](03-skill治理.md)）
3. **约束**：怎么用任务书、提示词和证据纪律，把不确定的模型压进确定的流程？（[04](04-提示词工程.md)、[05](05-工程纪律.md)、[06](06-踩坑实录.md)）

## 架构演进线（本手册的灵魂）

```
三角色最小模型                              3.0 多 Agent 架构
────────────────────────────           ────────────────────────────
项目所有者 × 顾问 Agent × 执行 Agent        所有者 × 协调者 × 执行/识别/多模态 × 独立复核
职责边界 · 单任务闭环 · 结构化执行提示词      L0/L1 授权包络 · 状态机 · Skill 治理
核心信条：                                同一组信条，一字未改：
  需求与设计先行                           显性需求优先于猜测
  执行与验证分离                           设计先于执行
  以证据而不是模型自述判定完成              范围锁定 · 证据优于自述 · 可回滚
```

最小模型解决的是「一个顾问 + 一个执行者」的三角关系；随着模型与工具变多，
3.0 把它推广成任意规模的多 Agent 拓扑——**但信条一字未改**：
需求显式化、设计与执行分离、用证据判定完成。

## 五条铁律（全文浓缩）

| # | 铁律 | 一句话 |
|---|------|--------|
| 1 | 显性需求优先于猜测 | 信息不足就追问，没决定的事不得伪装成既定事实 |
| 2 | 设计先于执行 | 需求确认前不进实现；先方案取舍，后动手 |
| 3 | 范围锁定 | 一次任务只解决一个主问题；禁止顺手扩面 |
| 4 | 证据优于自述 | 没有测试/构建/真实运行证据，不得宣布 PASS |
| 5 | 可回滚 | 重要变更先立基线；回滚必须写清代码/数据/配置怎么退 |

## 适合谁

- 用 AI Agent 做**长期项目**（而非一次性问答）的开发者与知识工作者；
- 正在搭「多个模型/多个 CLI 互相配合」流程，发现**没有制度就会互相踩脚**的人；
- 想给团队立一套「AI 产出怎么验收」标准的技术负责人。

## 快速开始（最小可用集）

1. 读 [01](01-架构总览.md)，定下你的角色表：谁是所有者、谁协调、谁执行——哪怕三者就是同一个人的三个会话；
2. 用 [04 的 10 要素](04-提示词工程.md) 写第一份任务书，执行端先过「动手前四查」；
3. 执行端交付只回 **结论 + 指针 + 三句话**，证据落盘（[02](02-设计与执行分工.md)）；
4. 全部产出按 [05 的状态词汇](05-工程纪律.md) 标注：PASS / FAIL / RISK / UNVERIFIED；
5. 每踩一个坑，回来改 [06](06-踩坑实录.md) 式的记录，并把它固化成一条规则——规则只保留解决真实重复问题的条文，防止无限膨胀。

## 角色速查（跨篇通用词汇）

| 角色 | 一句话职责 | 不能做 |
|------|-----------|--------|
| 项目所有者（人类） | 定目标、批包络、做最终验收 | 不替模型猜细节；不因自述「完成」而发布 |
| 协调者 Agent | 澄清、拆包、路由、回收、复核、写状态 | 不亲自下场实现（默认）；不冒充看过没看的材料 |
| 执行 Agent | 调查、最小实现、测试、交证据 | 不扩范围；不写状态；不用「看起来对」代替证据 |
| 识别 Agent | 读图/读表/读界面，审核生成结果 | 不改图不生成；越档需求退回拆包 |
| 多模态 Agent | 图片修改/生成、复杂多模态执行 | 不自证达标（须识别档审核）；不写项目状态 |
| 独立复核 Agent | 新窗口、只看产物与判据 | 不参与过执行思考链，否则失去独立性 |

## 术语表

- **授权包络**：任务开工前冻结的目标/范围/数据等级/禁止项集合（01 §3）；
- **交接包**：落盘成文、可跨会话跨 Agent 的任务契约（02 §5）；
- **四查**：执行端动手前查授权→skill→工具→缺口（03 §2）；
- **10 要素 / 11 模块**：任务书要素表与执行提示词结构（04 §3–4）；
- **状态词汇**：PASS/FAIL/RISK/UNVERIFIED/DEPRECATED/LEGACY（05 §2）；
- **单一真源**：状态文件只有一个写入者、skill 只存一份（02 §5、03 §5）；
- **RUN 报告**：执行端落盘的过程与证据档案，回传只给指针（02 §5）。

## 本手册怎么演进

按规则自身的维护纪律（01 §5）：新增规则必须解决**真实重复发生**的问题；
只新增不改写已冻结条文；项目特有细节不入此通用手册。
欢迎你按同一纪律向本仓库提 PR——附上触发这条规则的真实事故。

## 适用与不适用

**适用**：单人多会话、小团队多 Agent、跨 CLI/跨模型协作、长期迭代项目、
知识资产（skill/提示词/文档库）治理。

**不适用**：一次性问答场景（制度成本 > 收益，直接问就行）；
无人值守全自动生产（本体系的底线恰是「最终验收归人」）；
需要形式化安全认证的场景（本手册是工程惯例，不是合规标准）。

## 采纳顺序建议（落地用清单）

1. □ 写下你的角色表：谁是所有者、谁是协调者、执行端有几个（哪怕全是自己开的会话）；
2. □ 定默认授权模式（推荐 L1 包络 + 两次决定），明确「哪些操作永远需要精确批准」；
3. □ 采用状态词汇表，禁止团队/Agent 输出「基本完成」这类词；
4. □ 用 10 要素改写你手头最重要的一份任务书，执行端跑一单完整闭环（回执只收指针）；
5. □ 给重复 2 次以上的失误立一条规矩（规则只新增不重写，防膨胀）；
6. □ 有方法论沉淀需求时，再上 03 的挂载与门禁机制——不要第一天就上全套。

## 本手册自己的诚实声明

- 制度是**权衡产物**不是普适真理：它用流程开销换低返工率与可审计性，
  在快原型、纯探索阶段你可能想砍掉一半——可以，但请有意识地砍并记录为什么；
- 所有数字（命中率、盘点占比、事故规模）来自真实实践但样本有限，
  迁移到你的场景时**先验证再信任**——这本身就是本手册的方法论；
- 手册中没有任何一条规则要求特定模型或特定厂商；如果某条在你的工具栈里
  无法落地，说明需要的是改写机制而不是放弃信条。

## 使用边界

- 本手册是**方法论**，不是某个工具的说明书；示例中出现的产品名（Claude Code、Codex、DeepSeek 等）仅为角色占位，可替换为任意等价 Agent。
- 所有案例均已通用化：真实人名、项目名、绝对路径与价格信息已做角色化/抽象化处理。

## English Abstract

This playbook documents a battle-tested operating system for long-running software
and knowledge work performed by a human owner together with multiple AI agents.
Growing from a minimalist three-party charter (owner / consultant agent /
executor agent) into a 3.0 multi-agent architecture with an explicit authorization
envelope (L0/L1, C1–C4), a strict design-vs-execution split, a shared state
vocabulary (PASS / FAIL / RISK / UNVERIFIED), governable skill libraries with a
single-source routing table and supply-chain gates, and a ten-element task-brief
format that freezes the contract before execution. Five iron rules hold it together:
explicit requirements over guessing, design before execution, locked scope,
evidence over self-reporting, and rollback-first. Everything here is rewritten and
generalized; product names are placeholders for any equivalent agents.
